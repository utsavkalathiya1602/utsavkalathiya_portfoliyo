Upgrading Angular from v11 to v19: A Step-by-Step Approach

By Utsav Kalathiya · 7 Oct 2026 · 5 min read

At WRT InfoTech I upgraded a production Angular application from version 11 to version 19, eight major versions in one project, alongside redesigning parts of its UI. Jumps like that look scary, but they become manageable once you follow a strict, repeatable process.

This post is that process: how to plan the upgrade, the loop to repeat for every version, and the version-specific changes that need the most attention between v11 and v19.

The golden rule: one major version at a time

Never jump straight from 11 to 19. Angular's update schematics (ng update) include automatic code migrations, and they are written to go from one major version to the next. Skip a version and you skip its migrations.

ng update @angular/core@12 @angular/cli@12
# build, test, commit, then:
ng update @angular/core@13 @angular/cli@13
# ...and so on up to 19

The official Angular update guide generates a checklist for each step. Open it for every version pair.

Before you start

  • Work on a dedicated branch and commit after every major version, so you can always step back one version instead of starting over.
  • Get the current app green first. If the build or tests already fail on v11, you won't be able to tell old problems from new ones.
  • Audit third-party dependencies. Every Angular-specific library (UI kits, charting, date pickers) needs a release that supports each version you pass through. Abandoned libraries are usually the biggest blocker, so find them before you begin and plan replacements.
  • Check the Node.js and TypeScript requirements for each target version. You'll need to upgrade Node more than once along the way; Angular 19 needs Node 18.19.1+, 20.11.1+ or 22.

The loop to repeat for every version

  1. Upgrade Node.js if the target version requires it.
  2. Run ng update @angular/core@N @angular/cli@N. The migrations run automatically, so read their output.
  3. Update Angular Material and the CDK to the same major version, if you use them: ng update @angular/material@N.
  4. Update other Angular libraries to their matching releases.
  5. Fix compile errors, then run the build, the tests and a manual smoke test of the main user flows.
  6. Commit, and only then move on to the next version.

What changes along the way (v11 → v19)

v12–v13: the end of View Engine

Ivy, Angular's current compiler and renderer, became the only option: View Engine was deprecated in v12 and removed in v13. Internet Explorer 11 support was dropped in v13. Version 13 also supports RxJS 7, which deprecates toPromise() in favour of firstValueFrom() and lastValueFrom(), worth cleaning up while you're there.

v14: typed reactive forms

Reactive forms became strongly typed. The update migration swaps your existing FormControl and FormGroup usages to UntypedFormControl and friends, so behaviour doesn't change. You can adopt real types gradually afterwards. Standalone components also appeared as a developer preview.

v15: standalone APIs and the Material MDC switch

Standalone components became stable. For apps using Angular Material, this is the version to slow down: the components were rebuilt on Material Design Components (MDC). The old versions stayed available through legacy imports, but the new ones have different DOM structure and styles. Expect visual differences, and custom CSS that targets Material's internal classes may break.

v16: every dependency must support Ivy

ngcc, the compatibility compiler that let old View Engine libraries run on Ivy, was removed. Any library that was never rebuilt for Ivy stops working here, which is why the dependency audit matters so much. v16 also introduced signals (as a preview) and required inputs.

v17: new control flow and new builder

Templates gained built-in control flow (@if, @for, @switch) and deferrable views (@defer). Moving off *ngIf and *ngFor is optional, and there's an automatic migration: ng generate @angular/core:control-flow. The legacy Material components were removed in v17, so the MDC migration from v15 must be finished first. A new esbuild-based application builder became the default for new projects, and existing apps can switch to it for much faster builds.

v18: zoneless preview and Material 3

Zoneless change detection arrived as an experimental option, and Material 3 theming became stable. For most apps this is one of the calmer steps.

v19: standalone by default

Components, directives and pipes are now standalone by default. The update migration adds standalone: false to everything still declared in an NgModule, so a module-based app keeps compiling unchanged and you can convert to standalone later, at your own pace.

Where the effort usually goes

  • Third-party libraries without Ivy builds (blocking at v16) or without releases for newer versions.
  • Angular Material's MDC rewrite (v15–v17): mostly visual regressions and custom styles to rework.
  • Stricter TypeScript in newer releases surfacing type errors that were always there.
  • RxJS 7 deprecations, which are easy to fix but scattered across the codebase.

Upgrade first, modernise second

Resist converting to standalone components, the new control flow or signals in the middle of the upgrade. Get to v19 with the app behaving exactly as before, ship that, and then modernise in separate, reviewable steps. Mixing "upgrade" and "refactor" in the same commits makes every regression twice as hard to track down.

Takeaway

A large Angular upgrade isn't one big leap. It's the same small, boring loop repeated for every major version: update, migrate, fix, test, commit. Plan around your dependencies, take Material and Ivy-only libraries seriously, and keep modernisation for after you've landed.
